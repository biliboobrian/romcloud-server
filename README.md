# RomCloud Server

[![Release](https://img.shields.io/github/v/release/biliboobrian/romcloud-server?label=version&logo=github)](https://github.com/biliboobrian/romcloud-server/releases/latest)
[![Docker Hub](https://img.shields.io/docker/v/biliboobrian/romcloud-server?label=Docker%20Hub&logo=docker&sort=semver)](https://hub.docker.com/r/biliboobrian/romcloud-server)
[![Serveur Docker](https://github.com/biliboobrian/romcloud-server/actions/workflows/server-docker.yml/badge.svg)](https://github.com/biliboobrian/romcloud-server/actions/workflows/server-docker.yml)

Serveur de [RomCloud](https://github.com/biliboobrian/romcloud-android) : la bibliothèque de jeux rétro (ROMs par système, scraping ScreenScraper, Libretro, LaunchBox, Steam…), l’interface web d’administration et l’API lue par les applications Android, Android TV et Windows.

## Dépôts RomCloud

| Dépôt | Contenu |
|---|---|
| [romcloud-server](https://github.com/biliboobrian/romcloud-server) | Serveur (Node.js, image Docker) : bibliothèque de jeux, scraping, API |
| [romcloud-android](https://github.com/biliboobrian/romcloud-android) | Application Android (téléphone, tablette) et Android TV |
| [romcloud-desktop](https://github.com/biliboobrian/romcloud-desktop) | Application Windows (Tauri) et son moteur intégré |
| [romcloud-pc](https://github.com/biliboobrian/romcloud-pc) | RomCloud PC : jeux PC sous Android (Winlator Cmod), application compagnon |
| [romcloud-native](https://github.com/biliboobrian/romcloud-native) | RomCloud Native : jeux PC traduits en ARM64 (prototype de recherche) |

Historique commun jusqu’à la version 1.105 : [romCloud](https://github.com/biliboobrian/romCloud) (archivé).

## Installation — Docker Hub

L’image [`biliboobrian/romcloud-server`](https://hub.docker.com/r/biliboobrian/romcloud-server) est publiée pour **amd64** et **arm64** (PC, NAS Synology/Unraid, Raspberry Pi 4/5).

```bash
mkdir -p romcloud/data && sudo chown -R 1000:1000 romcloud/data
docker run -d --name romcloud --restart unless-stopped \
  -p 8080:8080 \
  -v "$PWD/romcloud/data:/data" \
  -e API_KEY=cle-des-applications   -e ADMIN_KEY=cle-d-administration \
  biliboobrian/romcloud-server:latest
```

Ou avec Docker Compose — fichier `docker-compose.yml`, puis `docker compose up -d` :

```yaml
services:
  romcloud:
    image: biliboobrian/romcloud-server:latest
    container_name: romcloud
    restart: unless-stopped
    ports:
      - "8080:8080"
    volumes:
      - ./data:/data                 # base de données, images scrapées, ROMs (./data/roms)
      # - /mnt/nas/roms:/data/roms   # ou un dossier de ROMs existant
    environment:
      API_KEY: cle-des-applications      # applications Windows / Android / TV (lecture seule)
      ADMIN_KEY: cle-d-administration    # interface web (accès complet)
      # Facultatif : scraping ScreenScraper (sinon Libretro seul)
      SCREENSCRAPER_DEV_ID: ""
      SCREENSCRAPER_DEV_PASSWORD: ""
      SCREENSCRAPER_USER: ""
      SCREENSCRAPER_PASSWORD: ""
```

Ouvrez ensuite `http://<ip-du-serveur>:8080` pour l’interface web d’administration (la clé d’API est demandée au premier accès).

| Tag | Contenu |
|---|---|
| `latest` | Dernier état de la branche `main` |
| `1.0.0`, `1.0`, `1` | Versions publiées (recommandé pour éviter les changements inattendus) |
| `sha-xxxxxxx` | Image d’un commit précis |

Mise à jour : `docker compose pull && docker compose up -d` (les données dans `/data` sont conservées).

Le conteneur s’exécute avec l’utilisateur `node` (uid 1000) : le dossier monté sur `/data` doit lui être accessible en écriture (d’où le `chown` ci-dessus), sinon lancez le conteneur avec `--user <votre-uid>`.

## Développement et configuration

Sans Docker, prérequis : **Node.js ≥ 22.13** (utilise le module SQLite intégré `node:sqlite`, aucune dépendance native).

```bash
cp .env.example .env      # puis renseigner API_KEY, ADMIN_KEY et, si possible, ScreenScraper
npm install
npm start                 # http://<ip-du-pc>:8080
```

Avec Docker : voir [Installation](#installation--docker-hub). Pour compiler l’image vous-même : `docker build -t romcloud-server .`.

**Publication automatique** : le workflow [`.github/workflows/server-docker.yml`](.github/workflows/server-docker.yml) teste le serveur puis publie l’image sur Docker Hub — `latest` et `1.2.3` / `1.2` / `1` sur un tag `v1.2.3` (`latest` aussi sur un lancement manuel depuis `main`). Secrets requis : `DOCKERHUB_USERNAME` et `DOCKERHUB_TOKEN` (jeton d’accès créé dans Docker Hub → *Account settings → Personal access tokens*, droits *Read & Write*).

## Utilisation de l'interface web

L’interface est disponible en **français** et en **anglais** : menu de langue en haut à droite (langue du navigateur par défaut, choix mémorisé). Les messages de l’API (erreurs, libellés des tâches, erreurs de scraping) sont renvoyés dans la langue demandée par le client (`Accept-Language`).


1. **Ajouter un système** → onglet *Catalogue Daijishou* : cochez les plateformes (SNES, PSX, GBA…) et importez-les. Le catalogue est complété par des plateformes fournies par RomCloud, marquées « RomCloud » (dossier [`platforms/`](platforms/), même format) : **Amstrad GX4000** (cartouches `.cpr`, cœur libretro `cap32`), distincte de l’Amstrad CPC. Elles arrivent avec leurs émulateurs, le filtre d'extensions, le nom Libretro et l'identifiant ScreenScraper. L'onglet *Personnalisé* permet de créer un système à la main.
2. **Ajouter des ROMs** : glisser-déposer dans la page (case « scraper automatiquement » cochée par défaut), ou copier les fichiers dans `data/roms/<dossier du système>/` puis cliquer sur **Rescanner**.
3. **Scraper** : bouton *Scraper les jeux* (toute la liste, en tâche de fond) ou depuis la fiche d'un jeu (ScreenScraper / Libretro au choix). Titre, description, date, genre, éditeur, jaquette et capture sont enregistrés sur le serveur et renvoyés à l'application.
   **Liste des jeux** : recherche par titre ou nom de fichier, filtre par **statut** (trouvés, introuvables dans les bases, pas encore scrapés, en erreur, ou tous les non trouvés) et par **note** (de 1 à 5 étoiles, note exacte, ou sans note) ; *Sélectionner…* permet de cocher plusieurs jeux (ou *Tout sélectionner* parmi ceux affichés) et de les **supprimer** d’un coup, fichiers, parties et images compris.
4. **Image du système** : dans *Réglages* du système, *Choisir une image* (PNG, JPEG, WebP ou GIF, 10 Mo max.) — logo ou photo de la console, affichée sur la carte du système dans l’application.
5. **Plateformes d’un système** : dans *Réglages → Proposé dans les applications*, décochez Android, Android TV ou Windows pour qu’un système (et ses jeux, recherche comprise) n’y apparaisse pas — ex. PlayStation 3 et Wii U : Windows seulement (moteur intégré avec RPCS3 et Cemu). Les applications envoient leur plateforme dans l’en-tête `X-RomCloud-Platform` ; toutes cochées = proposé partout.
6. **Jeux en plusieurs fichiers** : les **disques** d’un même jeu (« (Disc 2) », « (Disk 2 of 3) », « [CD2] », « - Disc B »…), ses **mises à jour** et ses **DLC** (« [UPD] », « (Update v1.2) », « [DLC] », identifiants Wii U 0005000E… / 0005000C…, paquets Sony `.pkg` — PS Vita, PS3 — dont le type (jeu, patch, DLC) est lu dans l’en-tête du paquet, ou à défaut dans l’identifiant de contenu « EP0001-PCSB00598_00-DLC0100000000000 » / « …_patch_01.02 », rattachés au jeu du même numéro de série ; ou titre du jeu suivi d’un complément — pas d’un numéro de suite) sont regroupés sous le jeu à chaque scan : une seule carte, la taille totale et la liste des fichiers dans sa fiche. Dans la fiche d’un jeu, *Détacher* en fait un jeu à part entière, et un fichier seul peut être *rattaché* à un autre jeu (comme disque, mise à jour ou DLC) ; ces choix manuels sont gardés aux scans suivants (*Revenir au regroupement automatique* pour les annuler). Supprimer un jeu supprime aussi ses parties.
7. **Émulateurs d’un système** : dans *Réglages → Émulateurs*, retirez les modèles inutiles ou ajoutez ceux d’un autre système (du serveur ou du catalogue Daijishou). Utile pour un système créé à la main (onglet *Personnalisé*).
8. **Doublons** (bouton dans la vue d’un système) : liste les **fichiers identiques** (même contenu sous plusieurs noms, vérifié par MD5 — les copies sont pré-cochées) et les **jeux en plusieurs versions** (régions, révisions : à cocher soi-même). Dans chaque groupe, RomCloud propose le fichier à conserver : sans marque de copie « (2) », pas de démo/bêta/dump défectueux, région préférée (`SCRAPE_REGIONS`), révision la plus récente, puis déjà scrapé. Les fichiers de plus de `HASH_MAX_MB` ne sont comparés que par leur titre.
9. **BIOS** (bouton dans la vue d’un système) : liste les BIOS **attendus par les cœurs libretro** des émulateurs du système (fiches [libretro-core-info](https://github.com/libretro/libretro-core-info) : chemin, requis ou facultatif, MD5 de référence) et les fichiers envoyés, avec contrôle des empreintes (MD5 et SHA1). Glissez les fichiers via *Ajouter des BIOS* : un fichier nommé comme un BIOS attendu est rangé dans le bon sous-dossier (ex. `dc_boot.bin` → `dc/dc_boot.bin`), ou utilisez *Envoyer…* sur la ligne d’un BIOS. Certains cœurs attendent un **dossier** (PCSX2 : `pcsx2/bios` et `pcsx2/resources`) : *Envoyer un .zip…* sur sa ligne envoie une archive de son contenu, extraite sur le serveur (chaque fichier devient un BIOS du dossier, téléchargé par les applications). Un .zip envoyé auparavant à la place d’un dossier est extrait automatiquement. Les MD5 de référence viennent de ces fiches, complétés par [`bios-hashes.json`](bios-hashes.json) (MD5 ou SHA1 par nom de fichier, dont les BIOS PlayStation `scph5500/5501/5502` v3.0 dont Beetle PSX contrôle le SHA1), complétable sans reconstruire l’image par un fichier `DATA_DIR/bios-hashes.json` de même format (`{ "scph5501.bin": ["490f66…", "0555c6…"] }`). **Un BIOS dont l’empreinte est connue est refusé à l’envoi s’il n’y correspond pas** ; un BIOS sans empreinte connue est accepté. Les fichiers sont stockés dans `DATA_DIR/bios/<système>/`. Les applications proposent ensuite de les télécharger avec le jeu. **Clés, firmwares et autres fichiers** des émulateurs sans cœur libretro sont listés au même endroit, avec leur type (BIOS, clés, firmware, données) et les émulateurs concernés : Switch `switch/prod.keys`, `switch/title.keys` et `switch/firmware.zip` (.zip des fichiers .nca, gardé tel quel) pour Eden, Ryujinx et Citron ; 3DS `3ds/aes_keys.txt` (Azahar) ; Wii U `wiiu/keys.txt` (Cemu) ; PS3 `ps3/PS3UPDAT.PUP` (RPCS3, aPS3e) ; PS Vita `vita/PSVUPDAT.PUP` et `vita/PSP2UPDAT.PUP` (polices) pour Vita3K ; Xbox `xbox/mcpx_1.0.bin`, `xbox/Complex_4627.bin` et `xbox/xbox_hdd.qcow2` (xemu). Les applications les téléchargent dans leur dossier BIOS comme les BIOS (et de nouveau quand ils changent sur le serveur) ; RomCloud pour Windows installe les clés de la Switch là où Eden et Ryujinx les attendent (dossier de l’utilisateur ou mode portable) à leur lancement, et le firmware PS3 dans RPCS3. Sous Android, les émulateurs externes importent eux-mêmes ces fichiers avec le sélecteur de fichiers, directement depuis le dossier RomCloud (`system/switch/keys/prod.keys`, `system/switch/firmware/firmware.zip`…), indiqué dans la fiche des jeux, à choisir depuis les paramètres de l’émulateur. **Dernières versions sur Internet** : pour les fichiers diffusés librement, la fenêtre indique la dernière version publiée, celle du serveur, et propose *Télécharger* ou *Mettre à jour* (taille contrôlée) — firmwares PS3 et PS Vita depuis les serveurs de mise à jour officiels de Sony, base de jeux de PCSX2 (`pcsx2/resources/GameIndex.yaml`) depuis GitHub. **Pilotes graphiques** (type « Pilote graphique ») : pilote Vulkan libre **Turnip** pour les puces Adreno (Snapdragon), `drivers/turnip.zip`, proposé pour la Switch (Eden, Citron), la GameCube et la Wii (Dolphin), la PS Vita (Vita3K), la PS3 (aPS3e) et la Wii U (Cemu, dont le pilote d’origine des Adreno 6xx plante : « failed to submit command buffer ») — dernière version depuis [K11MCH1/AdrenoToolsDrivers](https://github.com/K11MCH1/AdrenoToolsDrivers/releases), *Télécharger* sur chaque système voulu. Seules les applications Android le téléchargent, avec les BIOS, si leur option *Télécharger les pilotes graphiques* est active (par défaut sur les appareils Snapdragon) ; il est rangé dans `drivers/turnip.zip` du dossier RomCloud, indiqué dans la fiche des jeux, à installer depuis le gestionnaire de pilotes de l’émulateur (Cemu : réglages graphiques, pilote personnalisé). Les clés et les BIOS sous droits d’auteur n’ont pas de source : ils doivent être extraits de votre propre console.
10. **Miroir des émulateurs** (bouton en haut de l’écran) : émulateurs externes que le serveur télécharge sur GitHub ou Forgejo et garde pour les applications (voir *Miroir des émulateurs externes*). Il n’y a plus d’envoi manuel d’APK : un émulateur Android hors du miroir s’installe depuis le Play Store (les APK envoyés par les versions d’avant, `DATA_DIR/apks/`, sont supprimés au démarrage).
11. Cliquer sur un jeu permet d'éditer ses informations, remplacer ses images, le télécharger ou le supprimer. **Jeux PC compressés** : dans la fiche d’un jeu PC, *Compresser les fichiers (xz)* range chaque fichier du jeu dans sa propre archive `.xz` (xz -9e, le format qui fait gagner le plus de place sur les exécutables et les données des jeux, devant zstd, brotli et zip), en tâche de fond ; *Décompresser les fichiers* revient aux fichiers en clair. Il faut l’outil `xz` (XZ Utils : présent dans l’image Docker, sinon à installer, ou `XZ_PATH` pour son emplacement). Les applications Windows, Android et Android TV téléchargent les archives une à une (les plus lourdes d’abord) et décompressent chacune dès sa réception pendant que les suivantes arrivent (barre de décompression sous celle du téléchargement) ; le jeu est jouable une fois tout décompressé. Installation refusée s’il n’y a pas assez de place. Les applications plus anciennes reçoivent les fichiers décompressés à la volée par le serveur. **Arguments de lancement des jeux PC** : dans la fiche d’un jeu PC, *Arguments de lancement* ajoute des options après son exécutable, ajoutées par l’application Windows au lancement (« -novid -steam », « -game ep2 »…). Jeu sur moteur Source (Valve) livré avec un émulateur Steam (REVEmu, SmartSteamEmu…) : « -steam » est deviné au scan, sinon le jeu s’arrête sur « Steam startup failed: missing interface » ; vider le champ le retire pour de bon. Son AppID Steam (scraping) est lu dans le `gameinfo.txt` du jeu que lance l’exécutable (« hl2 », ou celui de « -game »), avant le `steam_appid.txt` : un pack Half-Life 2 et ses épisodes est reconnu comme Half-Life 2. **Jeux sur CD convertis en CHD** : dans la fiche d’un jeu PlayStation, Saturn, Mega-CD, Dreamcast, PC Engine CD ou PlayStation 2, *Convertir en CHD* compresse son image de disque (`.cue` et ses pistes, `.gdi`, `.toc`, `.iso`, ou l’archive `.zip`, `.7z` ou `.rar` qui en contient une, un disque par archive) en un seul fichier `Jeu.chd` avec l’outil `chdman` de MAME, en tâche de fond (suivie dans Tâches), avec les autres disques du jeu ; `.iso` de la PS2 en DVD (`createdvd`), le reste en CD (`createcd`). Le CHD, bien plus petit qu’une image brute, est lu directement par les cœurs du moteur intégré (sans extraction) ; la fiche du jeu est gardée (jaquettes, sauvegardes, temps de jeu), les fichiers d’origine supprimés une fois le CHD écrit (gardés si la conversion échoue). Les applications téléchargent le `.chd` la fois suivante. Il faut l’outil `chdman` (présent dans l’image Docker, sinon paquet `mame-tools` ou MAME, ou `CHDMAN_PATH` pour son emplacement) et, pour les `.7z` et `.rar`, `bsdtar` de libarchive (présent dans l’image Docker, sinon paquet `libarchive-tools`, `tar.exe` de Windows, ou `BSDTAR_PATH`). PSP, GameCube et Wii ne sont pas proposés (PPSSPP, Dolphin : autres formats).
12. **Version et mise à jour des jeux PC** : la fiche d’un jeu PC affiche sa *Version*, devinée au scan dans le nom du dossier (« Jeu v1.2-GOG », « Jeu.Build.12345678-TENOKE », « Jeu (1.0.4) ») ou, à défaut, dans l’exécutable du jeu (version de Windows du fichier, sauf jeux Unity et Unreal Engine, dont l’exécutable porte la version du moteur) ; elle peut être saisie à la main (vide : devinée de nouveau). Nouvelle version d’un jeu : ajoutez son dossier à côté (ex. « Jeu v1.3-GOG »), puis dans la fiche de l’ancien, *Nouvelle version du jeu* → *Remplacer par cette version* : ses fichiers remplacent ceux du jeu, qui garde sa fiche, ses images, ses sauvegardes et son temps de jeu (l’ancien dossier est supprimé). Remplacer les fichiers directement dans le dossier du jeu marche aussi. Les applications Windows, Android et Android TV signalent alors le jeu téléchargé (« Nouvelle version sur le serveur ») et proposent *Mettre à jour le jeu* : seuls les fichiers changés (taille ou date) sont téléchargés de nouveau, ceux retirés de la nouvelle version supprimés ; les fichiers créés par le jeu (sauvegardes, réglages) restent. **RomCloud PC à jour** : sous Android et Android TV, avant chaque lancement d’un jeu PC par RomCloud PC, sa dernière version publiée est vérifiée ; plus récente que celle installée, elle est proposée comme la mise à jour de RomCloud au démarrage (modifications depuis la version installée, *Mettre à jour* ou *Plus tard*, qui lance le jeu avec la version installée). Sans réseau, le jeu se lance aussitôt (5 s d’attente au plus).
13. **Options des émulateurs intégrés** (moteur intégré de Windows, émulateur intégré d’Android, RomCloud PC) : dans *Réglages → Options des émulateurs intégrés* d’un système, choisissez les options par défaut de ses cœurs (résolution interne, rendu, région…) ; dans la fiche d’un jeu, celles qui lui sont propres remplacent celles du système. Pour les jeux PC, ce sont les réglages de RomCloud PC (Proton, pilote graphique, DXVK…). Les choix faits par un joueur pendant la partie (ou dans la fiche du jeu PC) l’emportent toujours ; *Réinitialiser* revient aux valeurs du serveur. Les listes proposées viennent des applications : chaque cœur lancé envoie ses options au serveur (une fois par version), et une option absente des listes peut être ajoutée à la main (clé et valeur).
14. **Paramètres** (bouton en haut de l’écran ; « Utilisateurs » auparavant) : profils des joueurs créés depuis les applications (ou ici, *Créer un utilisateur*). Pour chaque profil : renommer, nouveau mot de passe (les appareils connectés sont déconnectés), désactiver, supprimer ; **appareils connectés** (nom, plateforme, version de l’application, adresse IP, dernière activité, connexion par mot de passe ou QR code — *Déconnecter* ferme une session), **temps de jeu par jeu**, **sauvegardes en ligne** et **erreurs** signalées par ses appareils. Onglets *Connexions* (toutes les connexions, réussies ou non, avec le motif d’un échec : mot de passe incorrect, utilisateur inconnu, compte désactivé, trop de tentatives) et *Erreurs des applications* (lancement impossible, téléchargement échoué, plantage de l’émulateur intégré ou de l’application, avec les détails). Réservé à la clé d’administration. Onglet **Erreurs** : erreurs signalées automatiquement par les applications (plantages de l’application et de l’émulateur intégré, lancements impossibles, erreurs d’interface, envois refusés) et **rapports** envoyés depuis leurs paramètres (*Signaler un problème* : description, appareil et journal de l’application ou du moteur intégré joints) ; hors ligne, les erreurs attendent le retour du serveur et gardent leur date. Onglet **Téléchargements** : journal de qui télécharge quoi sur le serveur (jeux, BIOS / clés / firmwares, APK d’émulateurs) — date, profil connecté ou anonyme, appareil, plateforme, version de l’application, IP, octets envoyés, reprise d’un téléchargement interrompu — et statistiques sur 7, 30 ou 90 jours (ou depuis le début), par type de fichier : totaux, par profil, par appareil, fichiers les plus téléchargés et volume par jour (un clic sur un profil ou un appareil filtre la page). Les applications joignent à leurs téléchargements le nom de l’appareil, leur version et la session du profil connecté. Onglet **Espace disque** : place utilisée par RomCloud et place libre sur les disques des données et des ROMs, en arborescence dépliable (chevrons) : ROMs par système, sauvegardes et historique des états par profil, BIOS par système, images, APK, caches (fiches des cœurs, LaunchBox), base de données et tout autre dossier du répertoire de données (calcul gardé une minute, *Recalculer*).

### Profils des joueurs

Une icône de profil, à côté des paramètres, permet de **créer un compte** ou de **se connecter** (Windows, Android). **Android TV** propose la connexion par mot de passe ou un **QR code** : dans l’application du téléphone déjà connecté, *Profil › Connecter une TV › Scanner le QR code* (lecteur des services Google Play, ou *Saisir le code* affiché sous le QR code), puis *Connecter* : la TV est connectée au même profil. Le profil garde :

- le **temps de jeu par jeu**, affiché dans la bannière de la liste des jeux et dans la fiche du jeu (émulateur intégré : temps de la partie affichée, menu fermé ; émulateurs externes : du lancement au retour dans RomCloud ; parties de moins de 10 s ignorées ; envoyé plus tard si le serveur est injoignable) ;
- les **sauvegardes en ligne de l’émulateur intégré** (état de la partie et mémoire du jeu, par cœur) : envoyées en quittant le jeu, récupérées avant de jouer si elles sont plus récentes — une partie commencée sur la TV continue sur le téléphone ou le PC (même cœur ; un état d’une autre version du cœur peut être refusé). La fiche du jeu indique la sauvegarde en ligne et propose *Reprendre*.
- l’**historique des états** de chaque jeu (émulateur intégré, Android, Android TV et Windows) : chaque *Sauvegarder l’état* (F2 sous Windows) et *Sauvegarder et quitter* ajoute un état daté avec une **miniature** de l’écran du jeu ; les **10 derniers par jeu et par appareil** sont gardés, plus les états **épinglés** (jamais supprimés automatiquement). *Charger l’état* (menu du jeu) et *États sauvegardés* (fiche du jeu, pour jouer à partir de l’un d’eux) listent ceux de l’appareil et ceux du profil en ligne, avec la **date, l’heure et l’appareil** d’origine : épingler, envoyer en ligne, supprimer (de l’appareil et en ligne). **Envoi automatique** réglable sur chaque appareil (*Paramètres › Envoyer les états en ligne automatiquement*, activé par défaut) : sous Android dès la sauvegarde, sous Windows à la fin de la partie (les états récents des autres appareils sont téléchargés avant la partie pour le menu du moteur) ; sinon bouton *Envoyer en ligne* sur chaque état. Hors ligne, l’envoi attend le retour du serveur.

Mots de passe hachés (scrypt), jetons de session aléatoires (seule leur empreinte est stockée), 10 tentatives échouées par quart d’heure et par nom d’utilisateur. Sauvegardes dans `DATA_DIR/saves/<utilisateur>/<jeu>/`, historique des états dans `DATA_DIR/states/<utilisateur>/<jeu>/`. Les applications **compressent** sauvegardes et états (gzip) avant de les envoyer, quand cela les réduit (états des consoles 8/16 bits, PlayStation, Dreamcast… : souvent 2 à 6 fois plus petits ; les états déjà compressés, PPSSPP, sont envoyés tels quels), et les décompressent à la réception : moins de place sur le serveur et moins de données échangées. Le serveur les garde tels quels ; les fichiers envoyés par une version précédente restent non compressés.

## Configuration (`.env`)

| Variable | Rôle |
|---|---|
| `PORT` | Port HTTP (8080 par défaut) |
| `DATA_DIR` | Base SQLite, ROMs et médias (`./data`) |
| `ROMS_DIR` | Dossier des ROMs, relatif à `DATA_DIR` ou absolu (ex. un NAS monté) |
| `DEFAULT_LANGUAGE` | Langue par défaut du serveur (`fr` ou `en`, `en` par défaut) : journal et clients qui n’envoient pas d’en-tête `Accept-Language` |
| `API_KEY` | Clé des applications (Windows, Android, Android TV) : à saisir dans leurs réglages. Avec `ADMIN_KEY`, elle ne donne accès qu'**en lecture** (consulter, télécharger) ; sans `ADMIN_KEY`, elle donne un accès complet. **À définir** si le serveur est accessible au-delà de votre réseau local. |
| `ADMIN_KEY` | Clé de l'**interface web** d'administration : accès complet (envoi, suppression, scraping, réglages). Recommandée, différente de `API_KEY` : une clé d'application divulguée ne permet alors pas de modifier le serveur. |
| `SCREENSCRAPER_DEV_ID` / `_DEV_PASSWORD` | Identifiants **développeur** ScreenScraper (à demander sur le forum screenscraper.fr). Sans eux, seul Libretro est utilisé. |
| `SCREENSCRAPER_USER` / `_PASSWORD` | Votre compte ScreenScraper (facultatif, augmente les quotas) |
| `SCRAPE_LANGUAGES` / `SCRAPE_REGIONS` | Priorités de langue/région (`fr,en` / `fr,eu,wor,us,ss,jp`) |
| `EMULATOR_REFRESH_HOURS` | Miroir des émulateurs : nouvelles versions des émulateurs gardés par le serveur récupérées toutes les N heures (`6` par défaut, `0` : seulement à la demande des applications) |
| `GITHUB_TOKEN` | Jeton GitHub facultatif pour le miroir des émulateurs (limite de l’API GitHub : 5000 requêtes par heure au lieu de 60) |
| `SCRAPE_CONCURRENCY` | Jeux scrapés **en parallèle** par une tâche (1 à 16, `1` par défaut). Avec ScreenScraper, borné par le nombre de requêtes simultanées de votre compte (`maxthreads`, 1 sans compte) ; une requête refusée pour ce motif (429) est réessayée. |

**Scraping** : ScreenScraper est interrogé par CRC32/MD5 + nom + taille (hachage jusqu'à `HASH_MAX_MB`, 1 Go par défaut). En cas d'absence ou d'image manquante, repli sur [thumbnails.libretro.com](https://thumbnails.libretro.com) (correspondance exacte du nom No-Intro, puis approximative). Les tâches s'exécutent une par une (jeux d'une tâche scrapés en parallèle selon `SCRAPE_CONCURRENCY`) et s'arrêtent si le quota ScreenScraper est atteint. **Jeux PC** : la boutique **Steam** (sans compte) les complète, y compris les jeux récents ou indépendants absents des autres bases : titre, résumé dans la langue préférée, développeur, éditeur, genres, date, jaquette (capsule de la bibliothèque Steam), captures et note des joueurs (part des avis positifs). Le jeu est retrouvé par son AppID, saisi dans la fiche du jeu (*ID Steam* : nombre ou adresse de la boutique) ou lu dans ses fichiers (`steam_appid.txt`, fichiers .ini des émulateurs Steam), sinon par son titre exact (plusieurs jeux du même nom : le plus commenté). Le titre est tiré du nom du dossier, groupe de release retiré (« Rock.Bottom-TENOKE » → « Rock Bottom »). **Informations détaillées** (section *Informations* de la fiche du jeu sous Windows, Android et Android TV) : autres titres et dates de sortie par région, régions et langues, série, modes de jeu, thèmes, classifications d’âge, numéro de série, version de la ROM (révision, beta, proto, disque…), résolution et rotation (arcade), vibrations et stick analogique, CRC32 / MD5, liens ScreenScraper et Wikipedia. Elles viennent de ScreenScraper, des fiches [libretro-database](https://github.com/libretro/libretro-database/tree/master/metadat) (par CRC, nom No-Intro / Redump ou numéro de série : développeur, éditeur, genre, date, joueurs, ESRB, série…) et du nom du fichier ; relancez le scraping des jeux déjà scrapés pour les obtenir. Jeux zippés : la ROM contenue dans l’archive (nom, CRC) sert à la recherche. Jeux d’arcade renommés (« fatal fury.zip » au lieu de « fatfury1.zip », Neo Geo, CPS, MAME…) : le jeu est retrouvé d’après les CRC des fichiers de l’archive dans la DAT de FinalBurn Neo, puis cherché sous son nom court. Jeu introuvable ailleurs : son article **Wikipedia** est recherché (titre du fichier, ou titre qui commence par lui sans être une suite, l’article devant alors citer la plateforme) ; il donne le titre officiel, le résumé, l’image de l’article comme jaquette, et via **Wikidata** le développeur, l’éditeur, le genre, les modes de jeu et la date de sortie ; libretro est ensuite réinterrogé avec le titre officiel pour les images.

**Sites de jeux rétro** : chaque jeu est aussi cherché par son titre dans **[LaunchBox Games DB](https://gamesdb.launchbox-app.com)** (base communautaire gratuite, sans compte, ~140 000 jeux). Son export complet (~110 Mo) est téléchargé au premier scraping puis une fois par semaine, et importé dans `data/launchbox/launchbox.db` (~200 Mo, plateformes rétro seulement). Il complète ce qui manque : résumé (en anglais, à défaut d’un résumé dans une langue préférée), développeur, éditeur, genres, date, nombre de joueurs, jeu coopératif, classification ESRB, note de la communauté, titres alternatifs, jaquette, capture et écran-titre, liens vers la fiche LaunchBox et la vidéo du jeu. Quand le jeu a un article Wikipedia, **Wikidata** ajoute sa série, ses modes de jeu et des liens vers ses fiches sur les sites de jeux rétro : MobyGames, GameFAQs, IGDB, RetroAchievements, HowLongToBeat, Killer List of Videogames, Guardiana, SMS Power!, Sega8bit, UVL, Kultboy, My Abandonware, VGMdb, StrategyWiki et speedrun.com.

**Note en étoiles** : chaque scraping combine les notes trouvées — ScreenScraper (sur 20), la communauté LaunchBox (sur 5, au moins 3 votes) et la presse relevée par Wikidata (Metacritic, GameRankings, Famitsu, IGN… : moyenne par site puis entre les sites, sur 100) — en une **note de 1 à 5 étoiles entières**. Chaque source a son barème, calé sur sa répartition réelle pour que les étoiles aient le même sens partout (5 étoiles pour les ~15 % meilleurs jeux, 4 pour les ~25 % suivants…) : ScreenScraper 17/20, LaunchBox 4,2/5 et presse 85/100 pour 5 étoiles ; 14, 3,7 et 75 pour 4 ; 11, 3,0 et 60 pour 3 ; 8, 2,4 et 45 pour 2 (barèmes dans `src/scraper/rating.js`). La note du jeu est la moyenne des étoiles des sources (une demi-étoile compte pour une entière). La fiche du jeu détaille la note de chaque source dans ses *Informations*. Une note saisie dans l’interface web est arrondie à l’étoile. Jeux scrapés avec une version antérieure : *Scraper les jeux* en répondant *Annuler* à « seulement les jeux non scrapés ? » pour recalculer leurs notes.

**Filtres** (Windows, Android et Android TV, liste des jeux d’un système) : en plus de *Tous / Téléchargés / À télécharger*, le bouton **Filtres** propose genre, décennie, nombre de joueurs (solo, 2 et +, 4 et +, coopératif), région, note minimale et éditeur, d’après les informations des jeux de la liste ; les critères se cumulent.

## Miroir des émulateurs externes

Les applications (Windows, Android, Android TV) ne téléchargent plus les émulateurs externes sur GitHub ou Forgejo mais **sur le serveur**, qui en garde une copie : un émulateur retiré d’Internet (dépôt supprimé, version effacée) reste installable. Émulateurs concernés : sous Windows Eden, Lichii, Orchid, Fritchii, RPCS3, shadPS4, KytyPS5 et Cemu ; sous Android ceux proposés en téléchargement direct (Eden, Flycast, Vita3K, ARMSX2, Cemu, aPS3e, MAME4droid, Winlator Cmod, RomCloud PC).

1. L’application demande au serveur les versions de l’émulateur ; le serveur interroge GitHub / Forgejo (liste gardée 15 min) et y ajoute les versions qu’il garde ;
2. pour la version à installer ou la mise à jour, l’application demande le fichier de sa variante (Eden PGO ou MSVC, APK « -sdk33 »…) : le serveur le récupère s’il ne l’a pas, l’application affiche la progression ;
3. une fois sur le serveur, l’installation ou la mise à jour est proposée et le fichier est téléchargé depuis le serveur.

Fichiers dans `DATA_DIR/emulators/<émulateur>/<version>/<fichier>` : plusieurs versions gardées par émulateur, listées et supprimables dans l’interface web (**Miroir des émulateurs**). Toutes les `EMULATOR_REFRESH_HOURS` heures, la nouvelle version de chaque variante déjà gardée est récupérée d’avance : la mise à jour est alors proposée sans attente.

## API

Toutes les routes (sauf `/api/info`) exigent `Authorization: Bearer <clé>` (ou `?key=`) quand une clé est définie : `API_KEY` pour les lectures (GET), `ADMIN_KEY` (ou `API_KEY` seule) pour les modifications ; une clé en lecture seule reçoit `403` sur une modification. Exceptions : `/api/account/*` (profil du joueur) accepte `API_KEY` même pour enregistrer ; `/api/users`, `/api/logs` et `/api/tokens` exigent la clé d’administration même en lecture.

**Clés d’accès générées** (interface web, *Utilisateurs* → *Clés d’accès*), en plus de `API_KEY` et `ADMIN_KEY` : chaque clé (`rct_…`) donne les mêmes droits que `API_KEY`, sur un nombre d’appareils choisi à sa création. Les applications envoient l’identifiant de l’appareil (`X-RomCloud-Device-Id`, ou `?device_id=` pour les images) : un appareil qui a utilisé la clé une fois prend une place ; une fois toutes les places prises, les autres appareils reçoivent `403` (`errors.tokenDeviceLimit`). L’administration peut libérer la place d’un appareil, changer le nombre d’appareils, désactiver ou supprimer une clé. La clé reste affichée dans l’administration, avec un bouton pour la copier et la partager (les clés créées avant cette possibilité n’en gardaient que l’empreinte : à recréer pour pouvoir les copier).
